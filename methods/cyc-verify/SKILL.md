# Verify the promised outcome

Establish behavior with checks actually run against current files. Follow the [handoff contract](../../docs/skill-contract.md), [code standards](../../docs/engineering/code-standards.md) and [progress standard](../../docs/response-standard.md#progress-updates). An advisory review may accurately report a defect; that does not satisfy a criterion that the product works. Label semantic judgment separately from executed results.

## The core loop

1. **Select relevant checks.** Inspect recipe list --run ID and each applicable prerequisite/effect/expected outcome. Execute authorized supplementary recipes; configuredCommandIds are already owned by final verification. Existing receipts are diagnostic history, not fresh external evidence. Use the project's preview/CSS/build setup before adding dependencies. Keep named state/action/outcome checks in the [existing recipe mechanism](references/recipe.md), not another mandatory report. Missing prerequisites or browser capability produce one precise limited result.
2. **Map decisive scenarios.** Retain every original criterion/material clause and affected consumer. Use one canonical scenarioEvidence observation per criterion/clause, mapping consumers to Scout IDs; finish derives exact legacy views. Record actual scenario, configured check, current-verification receipt, passed result, agent-reported origin and evidence. Missing/unavailable execution stays unverified; prose and suite counts cannot become machine-observed semantic coverage.
3. **Exercise authority together.** A new protected consumer requires the existing authoritative state-changing entrypoint → existing status → new protected read/write operations in one named journey. Use query-aware isolated storage/session adapters and actual handler behavior, including conflicting canonical/legacy representations. Cover canonical-only, legacy-only, ordinary transition and applicable eligible/unauthenticated/other-resource controls. Reuse a shared authoritative resolver or explicit reconciliation. Declared Scout journey names must match the scenario record; do not merely flip an invented status flag.
4. **Exercise asynchronous identity.** Validate actor/resource/operation context before acknowledging sends or merging reads. Test mismatched send identity while props/caches stay unchanged, mismatched reads/resources, older operations/contexts and delayed empty polling after a confirmed send. Invalidate stale context without falsely acknowledging the draft. Keep loaded-empty distinct from not loaded. Authorization remains server-owned: client rejection cannot reverse a completed write; preventing switched-session writes requires a separately tested server-verified expected-session precondition.
5. **Run the actual journey.** Prefer an existing behavioral test, then a focused boundary test, CLI/API trial, or supported browser journey. Check reload/persistence, error/retry and relevant negative cases. For record recreation inspect stored fields/references/access metadata beyond the UI projection using the [preservation contract](../../docs/engineering/failure-handling.md#preserve-records-when-an-operation-recreates-them). Known CYC development fixtures demonstrate these contracts; they do not prove a model finds unseen defects.
6. **Keep browser auditing external.** Reuse the host's actual documented API and current handles; do not guess methods/variables. Declare proportional desktop/phone and applicable send/reload, empty/error, membership-loss, overflow, keyboard/history/focus checks. Run supplementary accessibility scanning from a separate harness/context with dependencies/artifacts in its designated scope. Never string-replace application layouts or rewrite CSS/build configuration for instrumentation. Batch independent observations only after known state and when host policy permits. Respect interruption and report incomplete coverage. For new visual design also apply the [generic-tells](../cyc-design/frontend-design/references/generic-tells.md#score-sheet) and [experience](../cyc-design/frontend-design/references/experience-review.md) checks; narrow repairs preserve identity.
7. **Finish context, proof and verification.** Finish first validates planned canonical records/index against actual target source, or returns needs-context with the remaining authoring input. Required feature learning cannot be none or only a general handoff. Finalize context before final checks; later edits require fresh verification. Structural validation cannot certify the explanation’s semantic truth. Use run finish --run ID --file FINISH.json --wait-ms 30000 as the normal entrypoint. Frozen proofCommands can target decisive tests on originals; --tests only chooses swapped files. Bug-fix/feature tests go red on originals; refactor characterization stays green. Keep original-only, original-plus-new-tests and candidate roles distinct. A broad original result is required to excuse a pre-existing broad failure; finish measures it when needed and can retain compatible focused treatment. Missing/corrupt originals or source conflicts halt safely; never manually reset source or locks. See [run-start originals](../../docs/runtime.md#run-start-originals).
   Finish returns needs-proof-review when judgment is required, with receipt/failure IDs, errors, unknown boundaries and the exact bound continuation file. Supply categories/reasons there and call its command. Missing new interfaces/module-load/setup failures are not existing behavioral defects. Bug fixes need a decisive behavioral boundary; feature proof may establish a new interface. Inadequate/stale/foreign/placeholder judgments cannot complete. Non-testable exemptions and genuine unavailable-proof limits must be honest. Successful steps resume only while compatible. Final checks stay broad; deterministic receipt reuse needs explicit suitability and matching source/tests/config/dependency/toolchain/environment inputs. External/freshness-dependent checks remain nonreusable.
8. **Review the source and interpret results.** Check intent, consumers, conventions and the [principles](../../docs/principles.md); trace domain ownership and partial-effect/recovery boundaries. Prioritize demonstrated critical state/identity transitions before cosmetics, retaining history continuity and keyboard/return focus. Resolve or justify dismissing findings with evidence; open findings block. Capture before review and use the generated record template with actual evidence/identity or null. Bounded scoped review can survive an unrelated edit only with unchanged reviewed files, criteria and dependency/contract context. Unknown impact requires broader review; never relabel stale coverage as fresh. Final context/ledger/source edits invalidate affected evidence.

## Done when

Each original criterion and consumer has current evidence and honest limits. A proof shows the named failures actually observed; it never establishes every new test failed or assigns a repaired-defect count. Passing a stage, model review, source fingerprint or self-authored score does not certify product correctness.

Unrelated baseline failures need compatible measured original evidence and an explicit reason. Verification rejects new/changed failures, changed-source stacks, unmatched non-test output, changed exits or truncated/incomparable evidence. Report accepted failures; do not weaken criteria or config to fit a budget. New regressions inside an already failing suite remain blocking. A silent process, timeout, cancellation and crash are distinct outcomes; wait on the returned handle for 30–60 seconds rather than discovering status through ephemeral locks.

## Anti-patterns

Reading alone is not verification; tautological/mirrored assertions and mocks that pass with broken entrypoints prove little. Exercise the user's surface and reload path. Do not retry flakes until green, reuse stale evidence, infer unavailable browser success, weaken criteria, skip failures or change protected configuration. An agent review is a judgment, not a command result.

## Routing failures

Use run recover --run ID after failure/interruption; keep failed receipts diagnostic and describe the specific observation, supported cause and next justified action. Missing executables and timeouts do not themselves diagnose an application defect. Preserve locks/backups and budgets; do not automatically message others or start a replacement budget.

An authorized implementation repair returns through Build with run retry --run ID --stage build --reason, then re-verifies relevant consumers. A missed consumer or disproved approach returns through Scout/Impact/Design as appropriate. Advisory work reports findings unless repairs are authorized. External prerequisites get an honest blocked handoff with the smallest needed user action. Changes after Verify require renewed relevant checks/review. Save proposed checks in existing run-local notes when durable recipe/config edits are outside scope; never change the active run's verification contract to pass. Existing user authorization persists.
