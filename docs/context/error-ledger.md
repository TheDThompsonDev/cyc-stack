## ERR-009 · resolved · A refused operation wrote the source hash cache

- **Signature:** `Git newline recovery refuses mixed original bytes rather than accepting equivalent normalized text` (test/runtime.test.mjs) fails its before/after inventory on a new `.cyc/runs/source-cache.json`, in the full suite only.
- **Area:** the hash cache write in `inspectSource` (scripts/source-snapshot.mjs) and the workspace lock in scripts/runtime.mjs.
- **Observed:** the full suite after cherry-picking parallel hashing (4bf61fa) had 1 failure in 454 tests. The test passed alone. With a 2.5 s pause before `proveRun`, it failed every time on both 4bf61fa and f96f962, and a logging copy showed the test process writing seven cache entries during the refused proof. The suite passed at f96f962 only because the fixture usually reached the proof within two seconds, before any file had settled.
- **Root cause:** ERR-007 limited cache writes to snapshots taken under the operation lock, but each snapshot still stored the cache as it finished. The proof's first snapshot ran under the lock and stored settled hashes before the proof refused, so a refusal changed the project.
- **Correction:** snapshots under the lock collect cache updates in a per-operation stage (`writeCache` accepts a stage object; later snapshots in the same operation read the cache from it), and `withWorkspaceLock` stores the stage with `saveCache` when the operation returns. `writeCache: true` still writes at once for direct callers. A fresh-context review of the first version found that discarding the whole stage on a refusal also discarded a repair: a refused completion whose full read disproved a stale entry (as a memory-mapped write leaves) left it in place, so the next verification compared that stale view with the bytes on disk, was marked unstable and was charged a failed attempt (its script: failures 1 → 2, against 1 → 1 at 4bf61fa). A stage now also records entries a full read proved wrong (same identity, other bytes, read unchanged), and an operation that throws removes those from the stored cache with `forgetDisproved` and stores nothing else. A second pass found the same gap on return, for an operation that catches a snapshot's error after it disproved an entry; `saveCache` now drops disproved entries too. Each is matched by its wrong hash, so a corrected entry stays. The same review moved `saveCache`'s path lookup inside its error handling and removed a retained-lock condition that could never apply on return.
- **Guard:** `test/repo-limits.test.mjs`: `size: a refused operation leaves the hash cache as it was, even when every file has settled` (a refused proof after a 2.1 s pause), `size: snapshots given a stage collect cache updates and reuse them; only saving the stage writes the cache`, `size: a refused operation still removes a cache entry its full read proved wrong` (fails when the `forgetDisproved` call is removed), and `size: saving a stage drops an entry a snapshot proved wrong before it threw` (fails when `saveCache` ignores disproved entries). The first lock test still checks that a successful operation stores the cache.
- **Evidence/limits:** controller run `ea58f2f6-5021-42b5-826a-116ab7222ed5`. The newline-recovery test with the 2.5 s pause passed three of three runs on the fix in a scratch worktree; the test itself is unchanged, so in the suite it still exercises the settled case only when the machine is slow.

## ERR-008 · resolved · First large-repository version weakened four guarantees it was meant to keep

After the third pass, the `checkUntil` write is retried and then given up instead of failing the operation, a check that has exited can no longer be reported as timed out, and the generated runner carries an `eslint-disable` header.
