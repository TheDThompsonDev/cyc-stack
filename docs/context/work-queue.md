# Work queue

Covers: scripts/queue.mjs, scripts/queue-board.mjs, scripts/hub.mjs, scripts/hub-page.mjs, docs/work-queue.md, docs/maintainers/work-queue-plan.md, docs/maintainers/queue-board-plan.md, docs/maintainers/hub-design.md, test/queue.test.mjs, test/queue-journey.test.mjs, test/queue-board.test.mjs, test/queue-board-journey.test.mjs, test/hub.test.mjs

## Current view

A work queue orders several runs. It is an ordered set of units, each an ordinary run with its own criteria, proof, checks and change record; the controller decides which unit may start. The user guide is docs/work-queue.md and the plan with its as-built notes is docs/maintainers/work-queue-plan.md.

Where things live:
scripts/queue.mjs holds validation (queueDefinition), the derived view (queueView), the start rules (bindUnit), the note of an admitted run (noteStart), the commands (createQueue, queueStatus, queueNext, decideQueue) and the advice for bound runs (queueAdvice). It reads and writes nothing itself: scripts/runtime.mjs passes it an io object (queueIO) and exposes queueCommand and queueOf.
A queue is stored at .cyc/queues/<queueId>/queue.json with its start files beside it. That folder is a controller path in scripts/source-snapshot.mjs, so queue files are never project source, and it holds a .gitignore of `*` so queues stay local without touching a project's ignore file or the installer's managed one.
A run joins a unit through the optional `queue: {id, unit}` field of run start. The run stores its binding in its own state (state.queue: id, unit, definitionHash, attempt, drift, and at completion the source hash and file hashes it completed at).

The rule everything else follows: a run's state.json is the only record of how a unit ended.
The queue file holds the frozen units, their hash, the recorded decisions and a note of each run it admitted (started: unit, run id, attempt). It holds no unit status. queueView finds a queue's runs by reading the run states that carry its id, and derives each unit's status from them.
This removes the window where a run exists but the queue does not know: the run record is what binds a unit. The note is written first, under the same project lock. The notes give the order of admission, and a note stands in for a run only when that run's state cannot be read: a noted run with no readable record counts as a run with status missing, which halts its unit. A start whose record cannot be written takes its note back (dropStart); if that fails too the unit reads halted, which fails closed. Without the note, deleting or corrupting a halted run's folder made its unit ready again with no decision recorded. Writing the note after the record and ignoring a failed write, as the first correction did, left the unit unprotected with nothing said.
The order of the notes is the order the queue admitted its runs in, and since one unit runs at a time it is also the order they completed in. The view uses that order, not clock times, to choose the unit that completed last and the attempts since.
A unit's attempts are ordered by the attempt number stored in the run, given under the project lock, and a run that has not ended decides the unit whichever attempt it is. Ordering by start time let a clock that stepped back make a stopped attempt, with its retry decision, count as latest while the retry was running.
A bound run stores the units hash it was admitted under, and a queue whose hash differs from any of its runs' is refused: units and hash rewritten together are caught once a run exists.

Unit status, from the unit's latest run: none yet is waiting or ready by its dependencies; running or paused is in-progress; complete is done; blocked, halted, exhausted, stopped or missing is halted unless a decision recorded for that same run says retry (the unit is ready again) or skip (skipped). A skipped unit does not satisfy a dependency. A cancelled queue marks every unit that is not done as cancelled.
The line is halted when any unit is halted, in progress when one is running, complete when all are done, ready when a unit can start, and ended when what remains is skipped or waits on a skipped unit.

Start rules, checked in startRun under the project lock before anything is written: the queue reads and its units match their hash; the unit exists and is ready; no other unit is in progress or halted; the playbook and the criteria equal the unit's (criteria are compared without regard to field order, and inferred criteria are refused); every allowedPaths entry is inside the unit's paths and at least one is given. The check uses the paths the agent asked for, so the context docs the controller adds for retention are still allowed. A start without the field takes none of this path.

Decisions: retry and skip need a halted unit whose latest run has ended (halted, exhausted, stopped or missing) and are stored with that run's id and the status it had (afterStatus). A decision applies only while that run still reads that way, so a retry never excuses a later failure of the same unit, and a decision made about a missing run does not pass the run when its record comes back as blocked or halted. A blocked run has not ended and takes no decision; it is resumed or stopped. Cancel needs every bound run finished or stopped. A queue whose units were edited is refused everywhere except cancel by its ID, which is the remedy the refusal names; a cancelled queue is not listed as unreadable afterwards. Every decision needs a reason and stores the calling session. Nothing verifies that a person made the decision; the entry skill tells the agent to record one only after the user chooses.

Drift: at start a bound run compares its run-start snapshot with where the line last stood: the snapshot the most recently completed unit completed at, or, when no unit has completed, the run-start snapshot of the queue's first run. It records the files that differ (first 50 and the total), the ones outside this unit's paths apart (outsideUnit), and the runs admitted since that did not complete (unfinishedAttempts, which can include a blocked run). queue next shows the same comparison against the current tree before the start, and for a halted line too, so the files a retry would start from are seen before a person decides. When a run record was lost before any unit completed, drift names the lost run and says the starting point is unknown instead of reporting nothing.
Those files were changed by an attempt that ended short of complete or by an edit outside the line; both are named because a retry starts from them. Drift is information, never a refusal: refusing would make a person revert their own edit made while a unit ran. So a retry after a scope-guard halt still starts from the out-of-scope file, and the record is what makes that visible.
The halt reason is the one the run recorded (stopReason in scripts/run-gate.mjs). A run that was blocked or halted and then stopped keeps the earlier reason, since stopping is how a blocked run reaches a decision. queue next's instruction follows the unit's playbook: one that starts with Scout adds scout and plan to the start file, another starts the file as written. An ended line offers the cancel decision.

Choices made with the owner's agreement (2026-11-19, recommended in the plan and not changed): queues are local; any halted unit halts the whole line; a unit's paths are a hard limit, and a run that changes a file outside them is halted by the existing scope guard.
One unit runs at a time because the scope guard halts a run when files outside its paths change, so two units in one checkout would halt each other.
Units carry outcomes and criteria, not steps, because earlier units change the code later units meet. A frozen unit cannot be edited; a queue whose units no longer match their hash is refused everywhere, and the remedy is cancel and create.

Observed before building (slice 0, an experiment outside the project): two feature runs back to back, with and without Git and with no commit between them. The second run started from the first run's finished files and its original-code proof failed only its own new test. So units need no commit between them. test/queue-journey.test.mjs keeps that assertion.

Limits:
The queue orders runs; it does not start them. Unattended running, parallel units, commits, merges and deploys are not built. Whether a headless host session loads project hooks is unobserved and must be tested in a real host before a runner is designed.
The rules bind only runs that carry the field. An agent can still start the same work as an unbound run; the entry skill forbids that, and nothing enforces it.
Queue and run files are editable local records, not attestation: a queue file and its runs edited together are not detected. A queue belongs to one checkout; sharing one across machines or worktrees is not designed.
A status or next read that lands between a start's note and its run record shows that run as missing for that moment; a decision or start made then is refused by the project lock. This was seen only with the window widened on a copy.
One unit at a time holds within a queue. Two open queues in one checkout can each run a unit, and those runs can halt each other through the scope guard.
A bound run may word its goal differently and may leave out evidenceVersion and requirements; only the playbook, criteria and paths are held to the unit.
A bound run's state stores a second map of file hashes at completion, the same size as the run-start map.
Reading the line reads every run's state.json. That is the cost of having no second copy of status; it has not been measured on a project with thousands of runs.
Nothing here shows that a queue makes delivery faster, cheaper or more reliable, or that someone who is not a developer can use it.

Queue board (2026-11-20): the queue has a board and a review seat, in scripts/queue-board.mjs, specified in docs/maintainers/queue-board-plan.md (first half; the second half, side-by-side builders, is not built). The code comments are short because the release has a size budget; the reasoning is here.
Where things live: a board is stored at .cyc/queues/<queueId>/board.json beside its queue, so it is controller bookkeeping and never project source. It holds the messages, the seats and the read marks. The module is functions over that record; scripts/runtime.mjs supplies the files, the clock, the caller's session and a lock of the board's own (withBoardLock, board.lock), and exposes the actions through queueCommand (post, board, wait, release, and next with a seat), boardOf for run results, completionHolds for completion and recordBoardReview for the receipt. scripts/queue.mjs gained lineOf, the queue with its derived view, and refuses the unit ids person and all, which the board uses for who a message is for.
A message is a question, a finding, an answer or a notice. It is stored once and never edited, with its author filled in by the controller. An item (question or finding) is open until an answer names it. Who an item is for is worked out from the unit's status each time it is read: a unit that is done, skipped or cancelled has nobody to answer, so its items are the person's. Nothing is rerouted in storage. A halted unit keeps its items, since it may be retried.
Who speaks. A caller is the session its host reports (and, in a native host, its gate key); --session names it only when the host reports none, so it cannot be used to speak as another conversation the host knows. With --run it is the run's unit: the caller must pass assertRunOwner, and a run with no execution record, which that rule lets anyone change, is also held to the session it recorded (speaksFor). The first candidate compared sessions in a way that admitted a caller with no session; the second dropped the comparison and left every run started from a queue start file open to any conversation; a review caught both. With --seat it is the reviewer, and the caller must be the conversation that took the seat (the seat stores that conversation's keys). With neither it is the person. A conversation that owns an open run of the queue, or holds a seat, and posts with neither is marked relayedBy and may only answer a question that is the person's: that is the ordinary case of one person telling the builder their answer, and it stops a builder from declining a reviewer's finding as the person.
Who may close an item: the unit it is for (a finding needs disposition fixed or declined, a question takes none), the person, or its author (a question with assumed and the assumption made, or either kind with withdrawn). A builder cannot post a finding; a unit cannot ask itself; a question or finding has exactly one addressee.
The lock: board writes take board.lock, held for one read and one write, never across a check, so a message can be posted while a check holds the project lock. A caller gives up after five seconds. A lock older than ten was left behind: one waiter takes a claim file, checks again that the lock is still old, and clears it, so two waiters cannot both remove it or remove a fresh one; a holder writes a mark into its lock and removes only a lock that still carries it. The lock and the board file are found through the queue's folder: resolving the lock file's own path with projectFile raced with the process removing it. queue status, next and board take no lock; a reader that meets the board file while it is replaced retries briefly.
Delivery: the result of a run command for a bound run gains a board entry, placed first because agents act on the head of a result, with the messages for its unit or for all and the answers to what it posted that it has not been shown (the newest 20, with a count of earlier ones), and with what holds the unit. The read mark is kept in the board file per run and per seat. It moves only on a command that is a checkpoint (not run status, recover, list or review) and only for the run's own conversation. An item the unit itself already closed is left out; one that someone else closed is shown with how it was closed, so a unit that starts later learns what the person settled for it. queue wait returns when something new arrives or after at most a minute. A message cannot interrupt an agent.
What holds a unit: completeRun refuses while a question or finding for the unit is open, while a question the unit asked is open, or while a reviewer holds the seat without a sign-off. run finish asks first, for a running run only, and returns needs-answer with the list before any check runs. A unit with no board is held by nothing. With a board, a queue or a board that cannot be read is an error, because what is held is unknown; the first version treated an edited queue as holding nothing, which released every hold. An item that lands after the check finds the unit done and is the person's.
The review seat: queue next --seat review records one seat per run for a second conversation, which must give a session and must not be the conversation that builds the unit; --wait-ms lets it wait for a unit to start. The reviewer starts no run and changes no file. A seat is active until its reviewer signs off, gives it up, goes thirty minutes with no post, read or wait, or the run ends; a new ready-for-review from the builder makes it active again and restarts the clock. Reading keeps a held seat but does not revive a lapsed one, and every reviewer command returns the seat's state and the current source hash. review-done must carry the source hash the reviewer read and is refused when the source is no longer that: the first version stamped the hash at posting, which signed off edits the reviewer never saw.
The receipt: recordBoardReview captures and records one peer receipt in a single call from the seat's findings and their answers (fixed is resolved, declined and withdrawn are dismissed, each with who closed it), marked led by the queue board. It is refused without a standing sign-off, while a later reviewer still holds the seat, with an unanswered finding, when the source differs from the signed source, when the same sign-off is already recorded, and when the scope guard halts the capture. A seat given up after its sign-off still counts. Because the receipt covers the whole source, context records are settled before review is asked for.
Choices: the recommended decisions were shown to the owner and not changed (a held seat blocks completion; the person answers for a unit that is not running). Read marks live in the board file, not in run state, so delivery needs no second write to a run's record. The change-record format was left alone: an assumption a unit went on with is shown by queue next to the units that depend on it, and queue status shows the person the latest said to them.
Limits: the board records what the controller was told and is an editable local file, not attestation. A run that recorded no session can be posted for by anyone who has its ID. The relay rule knows a builder or reviewer only by its session and only while its run is open or its seat held; a caller with no session and no part in the queue is the person. The reviewer shares the builder's folder and is trusted to change nothing. Stop treats a reviewer correctly only through the existing rule that another conversation's run accounts for files in its scope.
Check: node --test test/queue-board.test.mjs test/queue-board-journey.test.mjs. The journey runs one feature unit with two conversations through the CLI: the reviewer's finding holds the unit, a sign-off on the source it first read is refused after the builder's edit, the sign-off on the current source releases it, the receipt comes from the board, and the unit completes with real original-code proof.

After the live trials (2026-11-20): two live trials ran in throwaway projects. In the first, one fresh session told only "Work the queue." worked three units in order with no hint. In the second, a builder session and a reviewer session, neither told how the board works, exchanged eleven messages in about three minutes: three findings, two of them real defects in the unit, two fixed and one declined with its reason, a sign-off on the final source, a receipt recorded from the board, and a completed unit.
What the trials showed wrong, and what changed. The builder asked the person a question and closed it with an assumption 68 seconds later; the person's answer came afterwards and was refused because the question was closed. A question whose only answer is its asker's assumption now takes one more answer, from whoever it was for or from the person (awaitsLate and lateAnswer in scripts/queue-board.mjs). It is delivered to the asker's unit at its next command while that unit runs and, once that unit is done, to the units that build on it directly or through other units (buildsOn, lateForGone): an independent review showed the first version reaching no agent in exactly that case. It holds nothing, and is shown as answeredLater on the board and in the assumed list queue next gives the units that depend on the asker. The asker cannot close the question again or give the answer itself as a relay of the person, a second late answer is refused, and a withdrawn question takes none. An answer for a unit that is no longer running is shown to the person in queue status, except an asker's own closing.
The builder's first command, queue next --session, was refused: every queue command now accepts --session, since the hook tells a conversation to pass it. The builder read the board module to learn the message fields: each hold's clear text now contains the message to post. queue status with no --queue after the line completed said only that no queue was open: resolve in scripts/queue.mjs now names the queue that finished last and the option that reads it, and still treats a finished queue as not open, which two existing tests fix.
Limits seen and kept: two sessions in one folder are told by the hook to draft their reply in the same file; the skill now says to use a file of one's own, and the hook's text is unchanged. A builder may still assume quickly; what changed is that a later answer is not lost.

The hub (2026-11-20): a person watches a queue from the hub. The owner said twice, after two live trials, that he never saw the agents talk: the exchange was in a board file and each session's chat showed only its own commands. The board was never the product; a person being able to watch is.
Where things live: scripts/hub.mjs holds hubState, which gathers what the page shows, and startHub, a node:http server; scripts/hub-page.mjs holds the one page it serves; bin/cyc.mjs has the hub command, which prints the address and stays running. The design decisions, palette with measured contrast and what was rendered are in docs/maintainers/hub-design.md.
The state is read fresh each time through what the controller already exposes and that takes no lock: queue status and queue board through queueCommand, and each run's history through readRun. It holds the queue (the one named in the address; otherwise the open one; with several open, the one being worked, then a halted one, then a ready one; with none open, the last one created), each unit with its status, what it waits on, what its run is doing, whether that run is paused and whether a reviewer is there, every board message with its speaker and addressee turned from the board's printed labels into roles, the ids that wait on the person, and the runs' history as sentences a person follows. A folder under .cyc/queues is listed only when it is named by a queue ID and its record carries the same ID. What waits on the person is what the controller lists for them, less the person's own questions (left open when their unit is skipped or done, they are nobody's to answer on the page) and nothing in a cancelled queue. A halted unit's reason is passed on with any run ID replaced by "its run". The hub writes nothing: no file, no lock, no read mark, so watching cannot change what an agent is shown; a test compares every file, the source hash and the board before and after many reads.
The server binds to 127.0.0.1, answers GET and HEAD on two addresses only, refuses a request whose Host is not the local address so that a page elsewhere cannot aim a browser at it, and sends a content security policy that allows nothing from outside. A request's address is compared as it was sent and never parsed as a URL: the first version parsed it outside any error handling, and one request with an unparsable address stopped the hub. The state is sent with a tag made from its content without the time it was read; a page that sends the tag back gets 304 and redraws nothing. Before listening, the hub connects to the port on 127.0.0.1 and ::1 and treats an answer as taken, because Windows lets a second listener on 127.0.0.1 start beside one on every address; without --port it scans 4780 to 4799 and says so when all are taken. cyc hub refuses any argument but --project and --port. The page loads no outside resource and places everything an agent wrote with textContent; words between backticks are shown as code. It asks for the state about every second and a half (every five seconds in a background tab), adds new messages without redrawing old ones, redraws the line, what waits and the activity only when their content changed (so focus and a selection survive), starts its lists again when the shown queue changes, tells a screen reader when more waits on the person, drops characters that reverse the text after them, and tells apart a hub that is gone from one that answers but cannot read the project.
Choices: read-only first, because answering from the page makes the hub a writer and needs its own rule for who is speaking. No dependency and no build step: node:http and one inline page. Polling, not a pushed stream: the records are files, a second is fast enough for a person, and a reader that only reads cannot hold anything open that an agent needs.
Limits: the hub shows what is recorded, so work between two controller commands appears when the next command records it. Unit states and run events are shown in plain words that the page maps from the controller's names; a new status or event appears under its raw name until a word is added. Nothing notifies a person whose tab is in the background beyond a count in the tab title. Answering and deciding from the page, and per-unit files and check output, are not built.
Check: node --test test/hub.test.mjs. It runs the page's own script in a small stand-in browser, so what the script does with a state is tested; the first tests only read the page's text and an independent review broke the hub fourteen ways without one failing. What the page looks like is still judged by rendering it.

## Lessons

- 2026-11-21 · run 14e344ec: My first hub tests read the page's text for forbidden words and never ran its script, so an independent reviewer broke the hub fourteen ways without one test failing. For a page, run its script against hostile and changing state; for a server, assert the exact headers and the bound address, and send it requests no browser would.

- 2026-11-20 · run 1c34bef4: A person answers on a person's clock. An agent that closes its question after a minute needs the answer to still have somewhere to go, or the record ends with an assumption the person contradicted and nobody was told.

- 2026-11-20 · run 595a60a5: A rule the tests wanted (another conversation must not post for a run) was first met with a second ownership rule of my own; it refused a run's real owner and admitted a caller with no session. Ask which rule the controller already has before adding one, and reuse it.

- 2026-11-20 · run 401a27ee: A rule the tests wanted (another conversation must not post for a run) was first met with a second ownership rule of my own; it refused a run's real owner and admitted a caller with no session. Ask which rule the controller already has before adding one, and reuse it.

- 2026-11-20 · run 4298ba9c: Keeping no copy of unit status in the queue removed the crash window between two writes, but a queue that keeps nothing cannot notice a lost run record: note what was admitted, and read the note only when the authority cannot be read.
