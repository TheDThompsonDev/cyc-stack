## Current view

startRun can freeze proofCommands for decisive regression/feature checks. The --tests option selects which test files are swapped and does not narrow the command plan. proveRun applies exact recorded originals, retains new tests, measures diagnostic red/green behavior and restores owned candidate bytes. Original-only, original-plus-new-tests and candidate receipts are distinct roles and cannot replace one another.

Candidate verification retains the full configured broad plan. Accepting a pre-existing broad failure needs compatible measured original broad evidence; a focused proof cannot excuse a changed/new broad failure. Existing baseline-cache storage is reused rather than adding another cache. Untouched focused treatment may be retained when compatible broad originals must be measured for a failure decision.

Receipt reuse is opt-in for declared local-deterministic checks. Inputs bind source/tests, commands, config, selected dependencies, environment and toolchain; unknown/linked/unbounded dependencies disable reuse. External or freshness-dependent checks do not silently reuse a local result. Actual CODEX tool-call transport metadata is removed from checks as well as fingerprints, while relevant environment changes and later context edits invalidate dependent evidence.

Source swaps publish candidate backups and owner records before changing files. Unexpected concurrent edits, invalid originals or incomplete restoration preserve recovery evidence and halt instead of overwriting unknown bytes. External editors remain outside controller locks; the workflow is coordination, not attestation or an atomic compare-and-swap.

Proof commands that name new test files (2026-11-20, run 1af64d5a): a focused proof command may name only test files the change adds, which is the natural plan for a feature with new tests. On the run-start code such a command finds no file and the runner exits non-zero before any test runs. proveRun used to read that exit as a check that already failed, and the proof was inconclusive. The control still runs and its result is kept in the receipt, but it is now read for what it shows. When a failed control printed no test results at all, and every failing test with the new tests added is in a test file this change added, the exit is read as nothing to run and those tests are attributed to the change: they did not exist at run start. The verdict says so, and the receipt records controlWithoutTests mapping the check to the added files that hold the failures.

The rule reads results, not arguments, so it does not depend on how the command is written: a shell string, a wrapper script or an option before the path behave the same. Every other case is judged as before. A control that printed test results is compared by name, so a wrapper that also runs existing tests keeps its "already failed there" note. Without named failing tests there is nothing to attribute: a mistyped path, a named file the change never creates, the dot reporter or an unsupported format stay inconclusive, and the verdict adds what would settle it. A failing test located outside the added files, for example one registered by an existing helper the new file imports, stays inconclusive because it may have failed before. So does a change that also deletes or moves a test file, because a test that already failed at its old path would look new. A control that timed out, could not start or had its output cut off is never read as nothing to run, and a control that passed is simply a passing control.

This was chosen over refusing such a plan at run start. The same plan already passed whenever the older skip applied (the new test fails by assertion and no other test file changed), and run start cannot know which case a plan will meet, so a refusal would have removed a plan that works. The first candidate skipped the control for a command whose test-file arguments were all new. An independent review showed that this assumed what the command runs: a wrapper that also ran an existing test was recorded as having nothing to run, and its earlier-failure note was lost. Reading the measured control replaced that. Limits: attribution needs test names and files in TAP, Jest or Mocha output; the unchanged TAP reader takes a nested "location:" line in an assertion diff as the test's file, which makes such a failure inconclusive (seen in review, not repaired here). Observed with Node 22: a mistyped name beside a real new file is ignored by the runner, and the proof rests on the named tests in the new file. test/proof-plan.test.mjs holds the working cases through run finish, each rejected case, a plan of several commands, the wrapper and a control that passes in silence. A second review of the measured rule found no wrongly passing proof; the conditions it found unpinned now each have a case.
