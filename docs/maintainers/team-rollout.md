# Team rollout

Start with a small team pilot on an approved version and host. Expand when installation, useful context reuse and verification work in that team's actual environment. A skills package needs understandable operation and ownership; a pilot does not establish enterprise readiness.

## Establish one working environment

Record the CYC revision, host, operating system, Node version and configured project checks. Demonstrate a real prompt/Stop cycle, an applicable rejected handoff and correction, and a bounded task. Follow [onboarding](../onboarding-recovery.md); missing activation evidence remains unverified.

Keep application verification in the project's own commands. Repository owners retain their existing review, CI and merge controls. Local editable CYC records are workflow evidence, not tamper-proof organizational enforcement.

## Check the handoff between people

One developer completes a change and retains a useful constraint or failed approach. A teammate uses a fresh checkout and chat to make a related change without the original conversation. Observe whether the relevant record is discovered, checked against current code and used correctly. Change a relevant dependency and check that stale guidance leads to investigation.

Assign context ownership through normal review. Keep Git-shared knowledge distinct from records that exist only in one checkout. Review context changes alongside the code they describe; a structurally valid document can still be wrong.

## Explain local records and support

Document what the host/provider and project commands may access. CYC does not launch model calls itself. Local records may include command output, source captures and interrupted-proof backups; Git ignore rules do not provide access control or retention enforcement.

Use the team's existing access and retention practices. Preserve active recovery evidence. Explain update ownership, the approved release, known host limitations and where support is available. Add organization-specific controls only where the team's requirements call for them.

## Gather optional feedback

Ask where setup required help, whether saved context changed a later decision, and whether users chose to continue. Volunteered examples can guide fixes. No usage collector, individual productivity ranking, token reporting or adoption dashboard is required.

Use [validation](../validation.md) to distinguish executed checks, agent review, native host observations and human acceptance. Keep unresolved required checks visible when deciding whether to expand the rollout.
