# Cohort adoption and public launch

Use the 60-person Dallas Software Developers cohort to establish a repeatable first task, a useful fresh-chat or teammate handoff, and a reason to use CYC again. Build public examples from that experience. The group sizes below are proposed stages, not measured adoption.

```text
5 volunteers → 20 participants → Up to all 60 → Outside developers and teams
```

## Show the user benefit

Lead with the problem: keep project decisions and lessons available across AI chats so the next developer can continue with context and checks they can inspect.

Demonstrate one saved constraint being found, revalidated and used in a later change. The website trial checks setup and product delivery; follow it with work in an existing repository where previous decisions matter. Keep speed, token-saving and enterprise claims within actual evidence.

## Expand when the experience works

Start with five volunteers on an approved release and qualified host. Give them one bounded task and note where they need help. Improve the guide, then invite twenty people in total. Have pairs try a handoff without the original conversation. Expand to the wider cohort when support is manageable and the documented installation works in the advertised environments.

Invite two or three willing participants to help reproduce problems and improve documentation. Use the cohort's existing communication channel. Follow the [team rollout guide](team-rollout.md) for host and context checks.

## Prepare the public launch

Complete [release qualification](distribution.md) before advertising the npm route as available. Publish a short demonstration and two or three participant case studies with permission. Include the task, useful retained context, actual checks, a difficulty encountered and remaining limits.

Point public posts to one home: the main repository and its quickstart. Start with Dallas community demonstrations and your professional network, then share relevant examples in agent and developer communities under their posting rules. Offer the repeatable exercise to other instructors once outsiders can follow it without private coaching. [Finding users](https://opensource.guide/finding-users/).

Provide one help channel, concise contribution guidance and a few small useful issues. Improve repeated installation questions in the guide. Welcoming documentation and responsive support make participation easier. [Community guidance](https://opensource.guide/building-community/).

## Keep endorsements voluntary

Invite a star after someone finds CYC useful. GitHub describes stars as bookmarks, appreciation and discovery signals. [Star guidance](https://docs.github.com/en/get-started/exploring-projects-on-github/saving-repositories-with-stars).

Invite forks for people who want to modify CYC or contribute. Installing it in an application does not require forking CYC. Keep endorsements separate from cohort participation. [Fork guidance](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/fork-a-repo).

Describe participation accurately: attendance, an assigned install and voluntary repeat use are different observations. Ask optionally what helped, what got in the way and whether someone chose to use CYC again. No telemetry system is needed. Ask before publishing names, quotes, screenshots or project material.
